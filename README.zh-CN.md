# xteink-toolkit

[English](README.md) | **简体中文**

**XTEINK X3**（阅星曈 X3）的字体与壁纸转换器。
528 × 792，259 ppi，4 级灰阶（SSD1677）。

三个独立命令行工具，把这台设备用的三种容器从零生成出来：

| 工具 | 输入 | 输出 | 用途 |
|---|---|---|---|
| `ttf2bin.py` | TTF/OTF | `.bin` | 1-bit 字体，无头，65536 槽 |
| `ttf2xtf.py` | TTF/OTF | `.xtf` | 2-bit 字体，64 字节头，区间索引 |
| `img2xth.py` | 任意图片 | `.xth` | 2-bit 全屏壁纸，4 级抖动 |

三种格式都没有官方文档，全部由逆向得出。证据与推导过程见项目内
`docs/XTF_FORMAT_SPEC.md` 与 `docs/XTH_WALLPAPER_FORMAT.md`。

---

## 安装

```bash
pip install pillow numpy fonttools
```

Python 3.9 以上。三个脚本各自独立，不共享模块。

---

## 快速开始

```bash
# 字体 → xtf：12 字/行，60 px 行高，46 px 字号裁到 43 px 宽
python ttf2xtf.py MyFont.ttf --em 46 --pitch-em 44 --grid-h 60 --face-width 43

# 字体 → bin：43×60 单元，46 px 字号
python ttf2bin.py MyFont.ttf -w 43 -H 60 --em 46

# 图片 → 壁纸
python img2xth.py photo.jpg
```

产物拷到 SD 卡：字体放 `Pushed Fonts/`，壁纸放 `Pushed Images/`。

## `ttf2bin.py`

| 参数 | 默认 | 说明 |
|---|---|---|
| `-w, --width` | 必填 | 排版步进（px），写入文件名 |
| `-H, --height` | 必填 | 行高（px），写入文件名 |
| `--em` | 同 width | 渲染字号 |
| `--threshold` | 0.5 | 墨迹覆盖率阈值，0..1 |
| `--boost` | 1.0 | 阈值前乘算，用于加粗笔画 |
| `--bold` | 0 | 合成加粗宽度（px） |

```
stride     = ceil(W / 8)          每行字节数
glyph_size = H * stride           每字字节数
total      = 65536 * glyph_size   固定槽数，没有头
位序       行内从左到右，每字节 MSB 优先
```

**每行字数由 W 决定**，实测规则 `floor(528 / W) - 1`：

| W | 528/W | 每行字数 |
|---|---|---|
| 40 | 13.2 | **12** |
| 43 | 12.3 | 11 |
| 44 | 12.0 | 11 |

W=43 与 W=44 都是 11 字——存储行按字节对齐（`ceil(W/8)*8 = 48` 位），两者
存同样的位图宽度。要 12 字落在 528 px 里，W 必须 ≤ 40。

`.bin` 是 1 bit，**没有抗锯齿**，这是格式决定的。要灰阶边缘只能用 `.xtf`。

## `ttf2xtf.py`

| 参数 | 默认 | 说明 |
|---|---|---|
| `--em` | 44 | 渲染字号，只影响绘制，**不写进 header** |
| `--pitch-em` | 同 em | 排版步进，写进 header `0x0a = pitch+1`，**决定每行字数** |
| `--grid-h` | 骨架值 | 行高 |
| `--face-width` | pitch−1 | 字面裁切宽度 |
| `--skeleton` | `skeletons/skel_g52.bin` | header/区间表/tail 来源 |
| `--cuts` | `64,128,192` | 2-bit 量化切点 |
| `--boost` | 1.0 | 阈值前乘算 |

### 两个 em 不是一回事

```
pitch-em  →  写进 0x0a = pitch+1，决定每行几个字（每行字数 ≈ 57 - 0x0a）
em        →  只是绘制字号，不写进 header
```

可以用 44 的排版步进配 46 的字号，得到「大字 + 12 字/行」。但字面会宽于步进，
必须损失点什么：

| face-width | 结果 |
|---|---|
| `pitch - 1` | 字间留 1 px 缝，字面被裁 |
| `pitch` | 无缝隙，相邻字紧贴 |

**裁切，不要压缩。** 把 45 px 重采样到 43 px 会让每一笔细 4.4%，偏旁明显缺肉；
裁切保持笔画宽度，只损失最右 2 px。

**裁切从第 0 列开始。** 测试字集的并集左边界不是安全起点——28 个常用字可能报
左边界 3，而「钧」这类字从第 0 列就起笔，从 3 开始裁会把金字旁的撇切掉。

### 每行字数

| `0x0a` | 每行字数 | 状态 |
|---|---|---|
| 45 | 12 | 已验证 |
| 46 | 11？ | **未验证** |
| 47 | 10 | 已验证 |

中间档只能靠真机确认。

## `img2xth.py`

| 参数 | 默认 | 说明 |
|---|---|---|
| `--dither` | `fs` | `fs` / `bayer` / `none` |
| `--fit` | `cover` | `cover` 裁剪填满 / `contain` 留白适配 / `stretch` 拉伸 |
| `--timestamp` | now | 写进 header 的 Unix 秒 |

```
22 字节头：魔数 "XTH\0" + 宽 + 高 + 保留 + 负载长度 + 时间戳 + 保留
两个 1-bit 平面，各 52,272 字节
level = (planeB << 1) | planeA     0 = 纸白，3 = 墨黑
```

**平面是列主序存的**：792 个连续比特构成图像的一列，且整体水平镜像。
解码要 `bits.reshape(w, h).T[:, ::-1]`，写的时候反过来。镜像不是 bug，是面板
的扫描顺序——漏掉这一步，壁纸会左右翻转。

**抖动实测结论**（同一台设备、同一张测试图）：

| 算法 | 真机表现 | 建议 |
|---|---|---|
| **Floyd-Steinberg** | 过渡细腻，16 级阶梯能分辨出 16 档 | **默认用它** |
| Bayer 8×8 | 几乎没有过渡感 | 不推荐 |
| 无抖动 | 只剩 4 个硬色块 | 仅线稿、图表 |

## 骨架文件

`ttf2xtf.py` 需要一份 17,920 字节的骨架，只包含：

```
0x0000..0x003F   64 B     header
0x0040..0x448F   17,488 B 区间表
0x4490..0x44EE   95 B     tail 表
0x44EF..0x45FF   padding
```

之后全是工具自己生成的字形数据。用骨架替代完整官方字体重新生成，输出
`SHA256` 逐字节相同（`2E2E42D4...FFD04308B`），已验证。

之所以不能从零构造，是因为 header 有三个字段没有已知公式，只能继承：

- `0x0d`、`0x0e`：用途不明
- `0x30..0x37`：8 字节，样本间不同，用途不明

其余 `0x0a`、`0x0b`、`0x0c`、`0x14`、`0x18`、`0x24`、`0x28`、`0x2c`、`0x38`、`0x3c`
全部重新计算。

`skel_g52.bin` 来自官方 40pt（gridH 52），`skel_g59.bin` 来自官方 46pt（gridH 59）。
两份骨架都只含元数据，不含字形轮廓。95 字节 tail 表也在
`docs/XTF_FORMAT_SPEC.md` §11.3 以十六进制完整记录，需要时可直接内联。

**字符集由骨架决定。** 工具按骨架的 19909 个码位逐个生成，字体缺失的码位留空。

## 兼容性

**只在 XTEINK X3（528×792，4 级灰阶）上验证过。** 固件里只出现过 `xteink.cn` 与
`X3-CH` 这类字符串，没有其他型号的痕迹，所以别的设备能不能用，目前没有证据。

三种格式对设备的依赖程度其实不一样：

| 格式 | header 里有屏幕尺寸吗 | 跨设备面 |
|---|---|---|
| `.bin` | 没有，尺寸在**文件名**里 | 最通用，纯按 W×H 解释 |
| `.xtf` | **没有**，只有 em / gridH / cellW | 结构上不绑定屏幕，但每行字数靠经验式 |
| `.xth` | **有**，宽高字段写死 | 头里留了尺寸位，其余设备理论上可覆盖 |

真正和设备绑定的是**屏幕宽度**，它影响两处：

```bash
# 每行字数的提示（不影响输出字节）
python ttf2bin.py font.ttf -w 40 -H 60 --screen-width 528

# 壁纸尺寸（会写进 .xth 的 header）
python img2xth.py art.png --width 480 --height 800
```

非 528 宽度的壁纸会打印一条提示：header 里带上了尺寸，但**没有经过真机验证**。
如果你在别的 XTEINK 型号上试成功了，欢迎开 issue 告知型号与固件版本。

`ttf2xtf` 的每行字数用的是经验式 `57 - 0x0a`，那个 57 是在 528 宽下拟合出来的，
所以它没有 `--screen-width` 参数——换个宽度这个式子就不成立了。

## 已知限制

- `.bin` 只有 1 bit，无法抗锯齿。
- `.xtf` 每行字数只有 45 / 47 两个实测点，46 未验证。
- `.xtf` 区间表不支持从 `cmap` 自动生成，固定跟随骨架。
- 骨架覆盖 CJK + 拉丁，不含 emoji 与扩展平面。
- `ttf2bin` 的渲染参数无法与任意既有 `.bin` 逐字节对齐——`.bin` 没有官方样本
  可反推，工具参数是一套可用的默认值。
- `img2xth` 的 Floyd-Steinberg 是纯 Python 循环，528×792 约需数秒。

## 验证状态

| 工具 | 验证方式 | 结果 |
|---|---|---|
| `ttf2xtf` | 重生成真机验证过的字体，比 SHA256 | **完全一致** |
| `ttf2bin` | 同参数重生成，渲染比对 | 字形一致，边缘因阈值差异略不同 |
| `img2xth` | 生成后按规格解码回读，比对 level 直方图 | **一致**，文件大小 104,566 B |

`.xtf` 有确定性证据；`.bin` 是视觉一致；`.xth` 是往返自洽。
